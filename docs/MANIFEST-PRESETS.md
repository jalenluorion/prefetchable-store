# Manifest keys for modes, profiles and defaults

`moved-store.json` carries three keys that describe the user-facing surface: `modes`, `profiles` and `defaults`.
The engine (`dmeng`, `dmserve`, the C API) reads them when they are present. A key the folder's manifest leaves out (a
manifest without `profiles`, or a folder without a manifest run with `--profile`) is taken from the published manifest
of the same family (`src/core/published_defaults.inc`, generated by `python/convert/published_defaults.py`), then from
the built-in values. Unknown keys are ignored, so a manifest may carry more than this file lists (notes, download
lists). The weight repos' manifests as this repository writes them are `python/convert/<family>/moved-store.json`.

The built-in values are one table for every model (`src/core/presets.cpp` BUILTIN): what differs between models is
declared in each one's manifest, never chosen in the engine by the model's name. What the table keeps is per profile, a
property of the device class:

- `mac`: the prefill's GPU share 0.4 / 0.4, run-ahead at depth 1;
- `phone`, `phone-small`: 8 readers, run-ahead at depth 1 limited to 0.2 of the token's compute, off while the readers
  are saturated, in `exact` mode only;
- `phone`: spare memory from 11 GB of physical memory, in both modes (`spare_memory`, below);
- `phone-small`: the 4-bit in-memory weights and the confidence names rule (0.5 of 16).

The run-ahead names the manifest's `experts.top_k` picks unless a profile gives `picks`. A profile must be declared in
the manifest (`profiles.<name>`), and a folder without a manifest has no profile (`--profile none`, unless the family's
published profiles apply).

Also declared per model:

- `resident.q8_rule`, required to derive the in-memory file: MLX's affine quantizer, 8 bits, groups of 64, the
  release's weights cast to `f16` or `bf16` first (the engine takes the cast from here).
- `drafting.cost_prior`, the drafting controller's prior: the cost of a pass of 0 to 8 positions over one step, used
  when it states where it comes from, `measured` or `estimated`; else the engine's neutral prior, a pass of n positions
  costing n steps. Either is replaced by the pass costs the engine has measured itself, `DIR/.dmeng/draft_cost.txt`.
- `prefill`, the batched prompt path's values (`include/dmeng/prefill.h`, the `prefill_<key>` options): `chunk`,
  `span`, `whole_from`, `gpu_min`, `short_names` (`router` or `none`), `join`, `waves`, `gpu_min_wave`, `pack_min`,
  `dn_rows`, `scratch_mb` (the prompt's scratch bound: `prompt_plan`, every family's rule: the sub-chunk at most a
  quarter, the fast path's MoE block at most a quarter, the span the rest, a short rest joined while the bound allows,
  equal spans; 0 = no bound), `lend` (with the server's or the C API's `prefill_release`, the cache lends the prompt's
  scratch estimate for the prompt), `apart` (the prompt kept apart from the decode's cache statistics, hazard policy; a
  profile's `prefill` block can set it, below), `fast` (the half-precision GPU prompt path in `fast` mode), `drop_upto`
  (`fast` mode: a prompt of at most this many positions keeps the decode's leave-out rule). dmeng (under a profile),
  dmserve and the C API all take the declared `chunk` and `span` (`prefill_chunk` resolves to 0, "the model's"); an
  explicit `--chunk` / `--span` / `--prefill-chunk` wins.

One engine runs all three models, Qwen3.6-35B-A3B (the 35B), Inkling 2 Mini and Qwen3.8-Flash-Next (expert store, cache, MoE steps, prompt path, server, drafting, counters). The rule:
every model gets the same behavior by default; a difference stays only where the model's architecture or released
files require it, or where a measurement shows the shared behavior is worse for that model (the numbers are in the
manifest beside the value). The table lists what differs.

## `modes`

```json
"modes": {
  "exact": {"definition": "Generated tokens never depend on the cache, the routers or timing.", "engine": "lossless"},
  "fast":  {"definition": "The model's router still picks; a picked expert that is not in memory is waited for if its routing weight is over 0.15 or its read is already in flight, otherwise it is left out.", "engine": "approx:drop:w=0.15"}
}
```

The engine reads only `engine` (the internal mode string: `lossless` or `approx:drop[:w=W]`). `definition` is for
people. `fast` mode has one leave-out method: `approx:drop:w=W`, a missing pick of released weight at most `W` is left out
(no substitute; the kept picks keep their released weights), a heavier one is read and waited for, and a pick whose
read is in flight is waited for; `w` defaults to 0.1. Built-in: `exact` = `lossless`, `fast` = `approx:drop`. The 35B
and Inkling 2 Mini declare `approx:drop:w=0.15` (measured on the iPhone: `modes.fast.calibration`), and the 35B's
`phone-small` profile declares `approx:drop:w=0.10` for its small cache (`profiles.phone-small.modes.fast`). Qwen3.8-Flash-Next
alone declares a capped form, `approx:drop:w=0.13:mass=0.13:late=-1` (its calibration: `modes.fast.calibration`): the
heaviest missing picks are read until those left out weigh at most `mass`, and a light pick in flight is left out
(`late=-1`; the default waits for it).
A profile can declare a mode's `engine` of its own (`profiles.<p>.modes.<mode>`, below), over this one for that profile.

    "mode": "exact",

## `defaults`

The 35B:

```json
"defaults": {
  "routers": ["linear_k2"],
  "names": {"rule": "confidence", "tau": 0.5, "candidates": 16},
  "cross_token": null,
  "priority_reads": true,
  "eviction": "auto"
}
```

Inkling 2 Mini:

```json
"defaults": {
  "routers": ["linear_k2", "mlp_k2_h512"],
  "names": {"rule": "confidence", "tau": 0.5, "candidates": 16},
  "cross_token": {"routers": ["xtok_s47_h512"], "source": 47, "tau": 0.5, "priority_reads": true},
  "priority_reads": true,
  "eviction": "auto"

```

| key | type | meaning |
|---|---|---|
| `routers` | list of ids from the manifest's `routers` | the early routers that name experts; the first id that resolves to a file is used; `[]` = none (cache only) |
| `names` | object | how many experts the routers name per step: `{"rule": "top", "m": 8}` (a fixed top m) or `{"rule": "confidence", "tau": 0.5, "candidates": 16}` (the top candidates whose calibrated probability is at least tau); either one per mode, `{"exact": rule, "fast": rule}`, as the profile key |
| `cross_token` | object or `null` | routers that name the next token's first steps from a late step of this one: `routers` (ids from `cross_token_routers`), `source` (the step they read, informational; the file carries it), `tau` (threshold), `priority_reads` (speculative reads by priority instead of first in, first out) |
| `priority_reads` | bool | speculative reads (router and cross-token names) by priority, nearest step first, instead of first in, first out (true for all three; `cross_token.priority_reads` counts as well). Applied where a names source runs: dmeng and dmserve take it (else on in `fast` mode or with the read planner, `priority_reads_on`); the C API applies it only with cross-token routers, the planner or `fast` mode, so the 35B and Qwen3.8-Flash-Next read first in, first out in its `exact` mode (not measured either way). Every front end reports the value in force as `resolved.priority_reads` (0 or 1) |
| `eviction` | string | `auto`, `hazard` or `freq` |
| `layer_caps` | string | per-layer slot caps: `auto` (the engine's rule), `uniform` or `none` (one pool), optionally with `:fit` (in a layer at its cap a name leaves min(2K + the loop holds, cap - names per step - the layer's own holds) slots free instead of 2K + the holds, so a layer whose cap holds its names admits them; the same wherever the cap is at least 2K + holds + names + the layer's holds); absent = `auto` |
| `drafts` | as the profile key `drafts` | the fallback for a profile that leaves it out (a bool also works: `true` = the lookup drafts) |

Inkling 2 Mini's default router is `linear_k2` (one linear layer, lag 2; engine file 49 MB, source
`routers/linear_k2.safetensors`): in one process with alternating segments it was 2 to 4% faster than the MLP
`mlp_k2_h512` beside run-ahead and reads about a fifth of the router bytes per token (44 against 222 MB). The MLP is the fallback when the linear file is
missing (the list's second id), and by explicit option (`--routers FILE`, `routers_id = "mlp_k2_h512"`).

Qwen3.8-Flash-Next (`qwen4_exp`; one profile, `mac`: `exact`, 8-bit in-memory weights, cache auto, names a top 4, the
GPU's share of the prefill 0.4 / 0.4, run-ahead naming 10 at depth 1):

```json
"defaults": {
  "routers": ["mlp_k4"],
  "names": {"rule": "top", "m": 4},
  "cross_token": null,
  "eviction": "auto",
  "layer_caps": "none"
}
```

Measured on the base M4 MacBook Pro, 16 GB (120 tokens of the reference prompt, counters from one process each, timing
from alternating runs), at 2.0 GB (15 records per layer) and 3.1 GB (24):

- `fast` mode: with 10 picks the routing weights are about 0.1 each, so a weight rule of 0.1 (wait for a pick over 0.1,
  leave out the rest) left out 0.32 of each step's weight. The rule here reads the heaviest missing picks until the rest
  weighs at most 0.13: 0.087 of the weight is left out on average (0.09 at the 90th percentile of tokens), at 465 MB
  read per token at 3.1 GB and 604 MB at 2.0 GB. A cap of 0.10 left out 0.066 at 650 MB (2.0 GB), 0.20 left out 0.15 at
  486 MB, 0.25 left out 0.19 at 419 MB.
- Names: a top 4 against a top 6, 10 and the confidence rule (tau 0.5 of 16): in `fast` mode 4 and 6 run at the same
  speed in alternating runs and 4 reads 6 to 9% less; 10 and the confidence rule read 785 to 918 MB at 2.0 GB, a third of
  their names wasted. In `exact` mode a top 4 in one pool ran 8% faster than a top 10 with per-layer caps in two
  alternating pairs (hit rate 0.58 against 0.49).
- One pool: below 2 x 10 records per layer the per-layer caps of `auto` refuse almost every name (a name must leave 20
  unpinned records in its layer: 241 of 352 names per token refused at 2.0 GB), so the cache runs on misses alone.

Its router entry `mlp_k4` points at `routers_k4.npz`, the lag-4 set as the trainer exported it (float32): the engine reads
the npz in place and derives its 8-bit file from it (step 4 below), the same bytes as the Python converter's.

The built-in `defaults`, used for any key the manifest leaves out, are the same for every model: no routers, a top 8,
no cross-token routers, eviction `auto`, no drafting (the profiles declare `drafts`). The names rule is a per-profile
value each manifest declares: the 35B and Inkling 2 Mini use the confidence rule (0.5 of 16) in `exact` mode on every
profile; in `fast` mode a top 3 on every profile of Inkling 2 Mini and on the 35B's `phone-small`, the confidence rule
on the 35B's `mac` and `phone` (on the Mac a top 3 doubled the 35B's loss against `exact` for a small gain);
Qwen3.8-Flash-Next uses a top 4 (measured, above).

## How an id becomes a file

For a router id `X` (or a cross-token id), the engine looks, in order, for:

1. the `path` of the manifest's `derived` entry `router.X.q8`, relative to the model folder (a folder downloaded from
   the Hub: `derived/router.X.q8.dmr1.<hash>.bin`);
2. `derived/router.X.q8.dmr1.<hash>.bin` in the model folder (the same name without a `path` key);
3. the same name as in 2 in the engine's own cache folder, `DIR/.dmeng/`;
4. otherwise it derives the file from `routers/X.safetensors` (or the router entry's `path`: an `.npz` is read in place)
   into `DIR/.dmeng/` (routers only; cross-token files are not derived by the engine, and the default is skipped with a
   note if none is found).

`<hash>` is the first 12 hex digits of the sha256 of the source part (`from[0]`). Every engine-ready file found this
way (and `embeddings.safetensors`, under `derived` or `parts`) is checked against the manifest's `bytes` and `sha256`
before it is used, once per version of the file (the result is kept in `DIR/.dmeng/checked/`); a router that does not
match is left out with a note, an in-memory file that does not match stops the run. The in-memory weights follow
steps 1 to 3 the same way; `resident_q8` is derived from `resident.safetensors` when missing, `resident_q4` is not
(`ms_derive resident DIR --bits 4` makes it).

A default that does not resolve (no file and nothing to derive it from) is dropped with one line on stderr; the run
continues without it. Tokens in `exact` do not depend on any of these files.
