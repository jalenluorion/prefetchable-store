Reading it:
- **FILE at the same 3.3 GB policy budget halves the drive reads** (163 -> 84 MB/token pitt, 202 -> 119 code) with
  **3.3 GB less footprint** (5.68 -> 2.40 GB): the OS kept 5.5-5.7 GB of store pages, and a miss the OS still holds
  costs a mincore and no read (47 of them per token on pitt, 83 MB/token skipped). Lower wait (16.4 -> 10.3 ms pitt).
- **No doubling of compute.** The engine session saw compute double when buffered pread copied into locked slots beside a
  locked cache; with views (no copy, no locked slab) compute is +7 % (pitt) / +21 % (code) over MLOCK in the same
  conditions, of which 1.4 ms/token is the use-time mincore check (cache_mgmt 0.5 -> 1.9 ms) and the rest the experts
  stage (+10 %, pages mapped from the file cache instead of wired anonymous memory). Under this contention the split
  is not finer than that; a quiet A/B is the one number left to take (section 6).
- **8 GB of bookkeeping buys nothing on a 16 GB Mac** that the OS's own 5.6-5.9 GB does not: the policy believes 8 GB
  is held, the OS keeps ~5.7, so 26-29 records per token are found gone at use (refaults, re-read as late misses):
  reads equal to FILE 3.3, more wait. The bookkeeping budget should follow what the OS keeps (section 6).
- **Under memory pressure the file tier shrinks under the policy.** The C API and Swift runs met another model
  process starting beside them (its guard does not know `dm_gate` / `PhoneStoreApp`), system swap grew 0.9-2.3 GB, and
  the OS kept only 0.68-0.79 GB of store pages: 120-145 refaults per token, 370-450 MB read per token, hit 0.44-0.57.
  The ids stayed identical (the point of those rows); their timings are not comparable and are left out of the table.

### The Mac probe (no model; `fc_mac_probe.cpp`, `fc_mac_probe*.json`)

Cold records of the common store, one thread: a buffered pread of a record leaves **all 108 pages resident for the
mapping** (mincore 108 / 108), and **no read-ahead spills into the next record** with F_RDAHEAD on or 0 (0 pages of
the next record resident either way; the order of the two halves, not the setting, decided which was faster:
0.87 / 1.57 ms and 1.56 / 1.11 ms reversed), so the engine keeps F_RDAHEAD 0. The first read through the mapping after
the pread still takes **108 soft faults** (0.08-0.11 ms per record; a second read 0.02 ms): the readers therefore
**prefault** (one byte per page, 0.044 ms per record on the reader thread), after which the compute threads read the
record with **0 faults** (0.032 ms). mincore costs **0.4 us for one page and 25.6 us for a whole record**: the use-time
check reads the first and last page (0.8 us; 300 checks per token = 0.25 ms), the readers' resident test the whole
range (once per miss, beside a ~1 ms read). **MADV_DONTNEED on a resident record leaves it resident** (108 -> 108,
also 200 ms later): the eviction hint does nothing measurable on macOS, so it stays off (`file_evict_hint` 0), pages
are left to the OS.

## 3. What was built

**Engine (port-ios)** - list of every shared-header change for the merge: `PORT-IOS-CHANGES.md`.
- `Mem::FILE` (store.h / store.cpp): layer files mapped read-only once; a held record is the view
  `fmap[L] + e * rec` (`Cache::rec`), the kernels take it as is; misses by buffered pread into a per-reader scratch
  (skipped when mincore says resident), then a prefault; slots are bookkeeping sized by `cache_bytes`; a held record
  is checked on use (first + last page) and re-read as an urgent late miss when gone (`file_refaults`); eviction drops
  the entry (optional MADV_DONTNEED); stats: held GB, MB read vs issued, refaults, resident skips, file-cache resident
  GB by mincore over all layer files (sampled at stats time). Open for a dirty tier in front: a second pool.
- Caller knobs: pool QoS and reader QoS (`CoreOpts::qos`, `reader_qos`; Pool ctor), threads / readers / core class
  from the C API, run-time cache budget (`Cache::set_budget` from any thread, applied at token and prefill-layer
  boundaries: shrink drops entries and gives memory back: munlock + MADV_FREE_REUSABLE, purgeable EMPTY, FILE
  bookkeeping only; grow up to the open budget), derived dir (`resolve_model(..., derived_dir)`,
  `Manifest::cache_override`), session disk dir, prefill progress (`LM::on_progress`, per layer in the batched prefill,
  per position in the default one) and cancel within one layer (the batched prefill restores the fixed state saved at
  the span's start: the state is consistent at `pos`), routers by manifest id (`routers_id`: `linear_k2`, `linear_k4`,
  `mlp_k2_h512`, `mlp_k4_h512`, `default`; none by default, as unified-wip), `Routers::mem` (iOS: plain, not mlock).
- `bindings/c/dmeng_c.{h,cpp}`: dm_open (opts: threads, qos, core_class, readers, cache_bytes, memory_mode,
  res_memory_mode, routers_id / routers, router_m, derived_dir, resident, disk_dir, disk_gb, ckpt_gb, park_gb, ctx,
  file_check, file_evict_hint), dm_close, dm_info, dm_sync (ids, marks, logits or NULL, progress callback ->
  reused / computed / source / ms / MB), dm_step, dm_cancel (any thread), dm_persist, dm_sample (penalties,
  temperature, top-k, top-p, min-p, seed: fixed integer / double arithmetic, draw seeded by (seed, draw index)),
  dm_argmax, dm_set_cache_bytes (any thread), dm_counters, dm_stats_json, dm_bench("filecache"). Platform defaults:
  iOS 4 threads, FILE, plain resident, checkpoints 0.2 GB, parked 0.3 GB; macOS 8 threads, MLOCK. Thread contract in
  the header. `tests/c_api/dm_gate.c`: the gate through the C API (also `--resize-at T --resize-gb G` and
  `--cancel-test`, not run: see section 6).
- `Package.swift` (repo root) + `apps/ios/DmengKit/Dmeng.swift`: the engine as a Swift package built from these
  sources (no binary; A16 flags; format code with `-ffp-contract=off` as in CMake; SME file excluded); `DmengModel`.
  `apps/ios/README.md`: where the app lives and how the two connect (engine-side pieces here, app-side in phone-store,
  so the move is a directory move plus one package path).

**Phone app (phone-store)** - `-engine dmeng` (MLX engine stays the default): `native/dmeng` link to this checkout,
`native/Package.swift` depends on it (DmengKit linked into PhoneStore and re-exported; DMBench's engine-kernel copies

### 7.2 Adaptive FILE budget

`Cache::FileAdapt` (`--file-adapt 1`, dm_open `file_adapt`, default on iOS): each token a rotating sample of 64 held
records is checked (first + last page) for the resident fraction (EMA), refaults per token are averaged (EMA ~8
tokens); every 8 tokens the budget shrinks toward resident fraction x held bytes (at least 5 % a step, not below the
floor) while refaults exceed 1 / token, and grows by 2 % of the ceiling while they stay under 0.1. The ceiling is the
open budget (`dm_set_cache_bytes` sets a new one); the floor `file_min_bytes` (default 1 GB). FILE shrink is now the
policy's choice (`file_compact`: lowest keep value first, survivors packed below the new cap; no bytes move). Stats:
`budget_gb`, resident fraction, refault EMA, shrinks / grows, the (token, budget) trace.

Functional check (A: code prompt, FILE, start and ceiling 8 GB, floor 1 GB, under the pressure described above, where
the OS kept 0.82 GB of store pages): the budget fell to the 1 GB floor in its first decisions (held 1.00 GB at token
50, 3 shrinks), stayed there while refaults stayed high (EMA 63 / token at the end, resident fraction 0.56: the OS
kept less than even 1 GB for us), followed the caller's lowered ceiling (2 GB at token 300) and came back to the
floor; ids identical. Its rates are not a measurement (pressure, overlap).

### 7.4 The campaign script for a quiet machine (the engine session runs it)

`results/ios/p1/file_vs_mlock.sh`: through the guard, resumable (skips runs whose log has a GUARD line), refuses to
start if a model process runs or QUIET is fresh, 400 tokens; `main`: per prompt (pitt, code) two repetitions of
MLOCK 3.3 | FILE adaptive (8 GB ceiling, 1 GB floor) | MLOCK 5.0 | FILE adaptive; `pressure`: FILE adaptive on pitt
while a helper holds 0 / 2 / 4 / 6 GB dirty; `core`: FILE adaptive + a locked core of 0.5 / 1.0 GB. Per run JSON,
the machine state at start (load, active + wired + compressed GB, file-backed GB, swap, power), ids checked against
the references, `fvm/summary.md` rewritten after each run (tok/s, compute, wait, MB read and issued per token, peak
footprint, file-cache resident GB, budget GB, refaults/token, others' memory / load, others' CPU). Command, from the
worktree (build first if `build/dmeng` is older than the branch):

    cd deep-memory/local/flash/github/moved-store-port-ios && cmake --build build -j3 --target dmeng && zsh results/ios/p1/file_vs_mlock.sh main pressure core

The locked core (`--file-core-gb`, dm_open `file_core_bytes`, store.cpp `core_init` / `core_refresh`): the hottest
held records of pool 0 by decayed count copied (pread) into an mlocked slab every 16 tokens (at most 32 swaps per
refresh), served from it by `Cache::rec`, pinned in the policy, never checked or re-read; the rest stays FILE. Built,
not run yet.
