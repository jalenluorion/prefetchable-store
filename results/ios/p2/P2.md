## 0h. Fast against Exact to the first token; the main-thread stalls (2026-11-23 07:35-08:00)

**Fast slower than Exact at once (7.3 / 5.8 / 6.4 s against 4.9 / 4.2 / 4.4): not the mode.** The prefill is the same
code in both modes: the prefill's early names are its own next-layer router (named 1773 / 1773 records in both runs of
the short message), the chat path passes mode, routers and tau explicitly (DmengChatEngine.load serves the chat and the
gate alike), and the per-layer caps are off during the pass in both. The 07:08 Fast rows had (a) a cold system state:
the per-mode saved-state folder keeps the two newest keys, and the launches between (other `approx:` strings) had
rotated Fast's out, so the system prompt was recomputed and the slab held its experts instead of the saved set
(4284 vs 3553 MB for the first message), and (b) a slower drive in those launches' reply prefills (0.53-0.58 GB/s
wall against 0.72-0.77 for Exact's, 0.75-0.79 for Fast's own warms). With the drive account around every prefill
(`-diagUI`: busy 96-99 %, 0.73-0.82 GB/s busy in all of them, Fast and Exact, warm and reply), Fast at once is 4.9 / 3.9 /
4.3 s against Exact's 4.8 / 4.0 / 4.2 s on the same build: equal to 0.1 s, every target met (<= 4.9 / 4.2 / 4.4).

**The stalls: the main thread waited for page-ins behind the engine's reads.** A sampler in the watchdog (main thread's
run state, CPU time and frame-pointer stack while a ping is late) showed the main thread *waiting* (run state 3 / 4,
0.00-0.04 s CPU over 0.5-4 s) inside SwiftUI layout, CoreUI image lookup, objc method lookup and the font parser: pages
iOS drops while the slab and the resident (2.55 GB locked) hold memory, faulted back in while 8 readers kept the drive
99 % busy with 1.77 MB records at the same I/O tier. Fix: (1) the readers' disk I/O one tier below the app's
(`setiopolicy_np(IOPOL_STANDARD)` on the reader threads; the option `reader_io_low`: CoreOpts, C API field, dmeng
`--reader-io-low`; default on for iOS only, off on macOS; CPU QoS unchanged; 08:08 check: on by default on the phone,
200-token reply with no stall over 250 ms, UI 4.51 / engine 4.48 tok/s); the reply prefills read at 0.73-0.81 GB/s with it (no loss); (2) the UI
follows a reply at most every 0.1 s (first token at once; the text, the stats bar and the prefill card in one update;
the card at most every 0.25 s), Markdown parsed once per text and unchanged blocks not rebuilt, the memory log and the
conversation file written off the main thread. Result (watchdog at 250 ms): no stall during the 300-token decode in

## 0f. First-token rows: pinned system state, relaunch at open, type-ahead (2026-11-23)

**Why a new chat did not restore the system prompt.** The reply's system mark came from `prefixIds([system])`, and the
Qwen template refuses to render a system message alone (no user query): the mark was never set, the warm-up
(`warmSystem`) returned silently for the same reason, and with the 47-token default prompt nothing was ever checkpointed
at the system boundary. Fixed: the boundary is where two renders of [system, user "a" / "b"] stop agreeing (the system
turn plus `<|im_start|>user\n`, 47 tokens for the default prompt, 439 with tools), as the MLX engine's
`Session.systemBoundary`; it is the first mark (pinned checkpoint, pinned disk file `prefix_*.pin.bin`).

**Why a relaunched chat recomputed the last reply.** The chat's disk copy was taken at the end of the history before the
reply (decode leaves no checkpoint), so the next turn recomputed the reply and the new message (39 positions). Fixed:
`persist()` at the live end checkpoints it first, and after every reply the app syncs (state only) the chat as the next
turn will render it, up to the next user header, and persists there; opening a chat restores that file (with its expert
set) in idle time.

Engine (phone-stage ca39d62, b921431): state-only `dm_sync` (NULL logits: a saved state at the end of the ids is restored
whole), persist at the live end, pinned system files kept by the disk LRU, chat files with the end and pinned states
only (was every checkpoint, ~63 MB each: 3.9 s of writes per reply), the pinned file's expert set refreshed at each
reply (a new chat's preload brings the last turn's experts, its generation header included), `dm_cancel_clear`,
`model_options` (iOS `prefill_release=1`). App (phone-store 7c35063): the boundary marks, `warm()` at launch / new chat /
chat opened / after each reply, the first token shown before its step, saved states keyed by (mode, in-memory weights
file), type-ahead.

**Type-ahead** (Settings "Read my message while I type", on by default; off in Low Power Mode, when serious / critical,
while a reply runs, while editing a sent message): at each word boundary (or a paste) the draft's stable part (all but the
last word, less one token) is synced in the background, state only, a checkpoint at its end; 300 ms after the last
keystroke the whole prompt as it would be sent is synced with its logits, so a send of exactly that draft computes
nothing; any keystroke cancels that speculative sync (`dm_cancel` + `dm_cancel_clear`); at send a running sync is kept
when its text is the sent text or a prefix of it, queued ones are dropped. Exact by construction (the prefix cache
restores only states it computed for the same ids).

## 4-bit resident format (resident_q4; what the loader reads, for a calibrated drop-in)

File `<model>/.dmeng/resident_q4.dmres1.<first 12 hex of resident.safetensors' sha256>.bin` (Qwen3.6-35B-A3B:
`resident_q4.dmres1.a603e898ddee.bin`, 1,135,001,600 B, sha256 07d18ccfc459038a393cff498c4821c5133fc0be7d4ed17a91336cb4961c8ba6,
made by `ms_derive resident DIR --bits 4`, 251 matrices, 1,114 tensors). Loaded by `dm_open` with
`resident_bits = 4` (or `resident = <path>`); the app passes it on a phone below 5.0 GB of available memory at open.

- **Container: DMENGRES1** (the same as the 8-bit file). A text header padded to 1,048,576 B: first line
  `DMENGRES1 <header bytes>`, then lines `cfg <key> <value>` (the model's engine config exactly as in the 8-bit file,
  plus `cfg resident_bits 4`), then one line per tensor `t <name> <dtype> <offset> <nbytes> <ndim> <dims...>`, then
  `end`. Offsets are relative to the end of the header, each tensor 16,384-byte aligned; dtypes `u8`, `f16`, `f32`, `bf16`.
- **A 4-bit matrix `NAME`** [R rows (outputs), C columns (inputs), C % 64 == 0] is three tensors:
  `NAME.q4` u8 [R, C/2] (row-major; two codes per byte, element 2j in the low nibble of byte j, element 2j+1 in the
  high nibble), `NAME.s` f16 [R, C/64] (per row, per group of 64 consecutive inputs), `NAME.b` f16 [R, C/64].
  Dequantisation: `w[r, c] = code[r, c] * s[r, c/64] + b[r, c/64]`, codes 0..15 unsigned. (The `.q4` suffix selects
  the 4-bit kernels; the 8-bit file uses `.q`, [R, C] u8 codes, same scale / bias layout.)
- **Which tensors are 4-bit** (exactly the 8-bit file's affine set): per linear-attention layer L: `L.qkv`, `L.z`,
  `L.o`; per full-attention layer: `L.q`, `L.k`, `L.v`, `L.o`; every layer's shared expert `L.sg`, `L.su`, `L.sd`;
  the output head `head` [248320, 2048].
- **Kept exactly as in the 8-bit file**: `L.a`, `L.b` (in_proj_a / in_proj_b), `L.router` (the released router) and
  `L.shgate` (shared-expert gate) in bf16; norms (`L.ln_in`, `L.ln_post`, `L.gnorm`, `L.qn`, `L.kn`, `norm`; the
  `(1 + w)` ones stored as 1 + w), `L.conv` [channels, 4], `L.A_log`, `L.dt_bias` in f32. No embedding table: rows come
  from `embeddings.safetensors` (or the manifest's file) as for the 8-bit resident.
- **Today's quantiser** (`src/format/quant.h`, MLX's `affine_quantize`, the F16 rule: the bf16 weight cast to f16
  first; per group of 64 in float32: w_min = min(group), w_max = max(group, 0); scale = max((w_max - w_min) / 15, 1e-7)
  with the sign / edge rule of MLX; bias = the edge; code = min(round((w - bias) / scale), 15); scale and bias stored
  as f16). A calibrated set only has to keep the layout: any codes / scales / biases in these shapes load as is.
- **In moved-store.json terms**: a derived variant `{"id": "resident_q4", "from": ["resident.safetensors"],
  "engine_format": "dmres1", "bits": 4, "sha256": "07d18ccf...8ba6", "variant_of": "resident_q8", "optional": true,
  "for": "memory-limited devices (approximate: tokens differ from the 8-bit resident)"}`; a calibrated export would
  carry its own sha256 and, if it should coexist, its own id (e.g. `resident_q4c`, file `resident_q4c.dmres1.<hash>.bin`,
  loaded with `resident = <path>`).

## 2b. The file cache on the phone (step B, on the old store's 15.67 GB of .psc files as bytes)

**B1: plateau of mapped store pages against dirty memory held** (`-fileCacheTest grow|dirty`, 8 sweep threads; 0 and
1.5 GB are P0's runs of this morning, 2.5 / 3.3 GB today 10:40 / 10:49, thermal fair -> serious during the sweep):

|---|---|---|---|---|

| **3.3 GB** | 3.33 | 0.96 | **2.93 / 2.2-2.7** | 0 |

**Answer: the OS keeps ~2.2-2.9 GB of clean store pages for the foreground app whatever dirty memory it holds, up to
3.3 GB** (the app's limit is 4.27 GB): the file cache is not taken from the app's budget. So the 8-bit resident loaded
as dirty memory (2.09 GB) costs the expert cache nothing, and **mapping the resident file-backed would make its 2.09 GB
compete with the experts for the same ~2.5 GB of file cache** (every token reads all of it: it would push out most expert
pages, or be re-read from the drive). Decision: the resident stays loaded (`res_memory_mode` PLAIN, the iOS default);
E4 (mapped resident) is a check of that prediction, not a candidate. The dirty budget left beside it (4.27 - 2.09 -
KV / prefix / scratch ~1.1 GB = ~1 GB) is better spent on a locked core of hot records (`-dmengCoreGB`) than left idle.

**B2: can the app drop pages it no longer wants?** (`-fileCacheTest drop`, 10:35, thermal fair: a target range of 64
records = 113 MB in layer 00's file and a control range of 64 records in layer 39's, both made resident, one method
applied to the target, mincore on both; then a re-read of the target):

| method | rc | call | target resident after (0 s / 1 s / 5 s) | control | re-read of the target |
|---|---|---|---|---|---|
| madvise MADV_DONTNEED | 0 | 0.54 ms | 1.00 / 1.00 / 1.00 | 1.00 | 0 page-ins |
| madvise MADV_FREE | 0 | 0.00 ms | 1.00 | 1.00 | 0 |
| madvise MADV_FREE_REUSABLE | EPERM | | 1.00 | 1.00 | 0 |
| madvise MADV_PAGEOUT (xnu value 10) | ENOTSUP | | 1.00 | 1.00 | 0 |
| **msync MS_INVALIDATE** | 0 | **3.69 ms (0.058 ms per record)** | **0.00 / 0.00 / 0.00** | **1.00** | **6,912 page-ins (= 64 x 108), 177 ms** |
| msync MS_KILLPAGES | 0 | 0.00 ms | 1.00 | 1.00 | 0 |
| msync MS_DEACTIVATE | 0 | 0.95 ms | 1.00 | 1.00 | 0 |
| munmap + mmap MAP_FIXED of the range | 0 | 0.56 ms | 1.00 | 1.00 | 0 |
| never touched while 6.0 GB of other records are swept; control re-touched every 0.5 s | | 12.8 s | **0.00** | **0.94** | |

**Answer: yes. `msync(MS_INVALIDATE)` on a clean read-only MAP_SHARED range drops exactly that range from the file
cache at once (0.058 ms per 1.77 MB record), leaving everything else** (the re-read pages in every page again: the
pages were really gone, not hidden). No madvise variant does anything on iOS 27.2 (the Mac's MADV_DONTNEED result in
P1 holds here too), nor do MS_KILLPAGES / MS_DEACTIVATE or unmapping. And the OS's reclaim follows use: a range not
touched while others stream goes first, a range touched every 0.5 s survives at 0.94. So **our policy can choose what
stays**: evict = MS_INVALIDATE the record, keep = touch it (the use already does). This makes EVICT.md's arrangement
B2 (one policy-managed tier over the whole file cache, hazard: 122 vs 139 MB/token for the OS's LRU at 3.3 GB on pitt)
buildable. Built on this branch: `file_evict_hint = 2` (store.cpp `drop()`; tool `--file-hint 2`, C API
`file_evict_hint`, app `-dmengEvictHint 2`), off by default; measured in E2b once the store is on the phone.

## 7. In-app download of the common files (built, 2026-11-23)

The Hub repo `jalenluorion/Qwen3.6-35B-A3B-moved-store` (commits f7781746c79e, 49aef8d4ad5a) carries the presets
structure; the app reads it (phone-store 9539286). The live `moved-store.json`:

- `profiles.<name>` for `mac`, `phone`, `phone-small`: `when`, `mode` (exact / fast), `resident` (resident_q8 /
  resident_q4), `precision`, `names` ({rule: top, m: 8} or {rule: confidence, tau: 0.5, candidates: 16}), `cache`,
  `cache_rule`, `bytes` (the sum of the listed parts; moved-store.json itself is fetched first and not listed) and
  `parts`: a list of OBJECTS {path, bytes, sha256}. phone-small: 49 parts, 20,352,447,020 B (40 store layers,
  `derived/resident_q4.dmres1.a603e898ddee.bin` 1,135,001,600 B sha256 07d18ccf...8ba6, no 8-bit copy,
  `derived/router.linear_k2.q8.dmr1.efd45c78a56b.bin`, `embeddings.safetensors` 1,017,119,224 B, config, tokenizer,
  template, LICENSE); phone and mac: 49 parts, 21,309,272,620 B with `derived/resident_q8...`.
- `layout`: engine-ready files under `derived/`, the engine's derived names; the engine looks in DIR/derived/ and
  DIR/.dmeng/.

**What the app does now** (ModelDownloader.swift, DownloadConfig.swift, `MovedStoreManifest`):
1. The manifest URL is the common repo's `moved-store.json` (`-downloadLegacy` keeps the old phone-format repo).
2. The profile: `download.profile` setting, else the device's (PRESETS.md: `phone` with >= 5.0 GB available at open,
   `phone-small` below). Its `parts` become the required files at their repo paths; its `bytes` the size on the Set up
   screen (before the manifest arrives: 20,352,447,020 / 21,309,272,620 B).
3. Files go to Documents/dmeng-model/ (the app-made folder, so it can write derived/), each SHA-256 checked, resumable,
   the same background session and progress as before. The verified-files record keys by path with size, mtime and
   sha256, so a part whose manifest hash changes (the calibrated resident_q4 under the same name) is re-verified and
   fetched again.
4. Done = DmengLaunch.completeness (the profile's resident in derived/ or .dmeng/, 40 layers, embeddings, tokenizer);
   the engine is opened with derived/ as its derived dir when it exists.
5. `-p2VerifyManifest FILE`: hashes every part of the profile where it is (repo path, or where a copy by cable put it:
   derived/X in .dmeng/X, the embeddings in Documents/model) and reports mismatches; nothing moves.
